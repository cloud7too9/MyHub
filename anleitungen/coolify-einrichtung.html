Coolify einrichten & Projekte ausrollen

⏱ ca. 45 Min Aktualisiert 04.08.2026 Ubuntu 24.04 LTS · Coolify v4

Einmalig Coolify auf dem Hetzner-Server aufsetzen und absichern — danach jedes Projekt aus GitHub anlegen, mit Domain versehen und bei jedem Push automatisch ausrollen lassen.

Die einmaligen Server-Schritte sind ausgeblendet — sichtbar bleibt der Weg, den du für jede neue Anwendung gehst.

1
Einmalig pro Server

Voraussetzungen prüfen

Coolify ist ein selbst gehostetes PaaS: eine Weboberfläche, die im Hintergrund Docker steuert und einen Traefik-Proxy für Domains und Zertifikate mitbringt. Der Server sollte vorbereitet sein:

  • Abgesicherte Grundinstallation — eigener sudo-Benutzer, SSH-Härtung, UFW und fail2ban nach Server-Erst-Einrichtung & Absicherung
  • Mindestens 2 vCPU, 4 GB RAM, 30 GB Platte — bei Hetzner also ab CX22. Mit 2 GB startet Coolify zwar, aber jeder größere Build läuft ins OOM-Kill
  • Freie Ports 80, 443 und 8000
  • Ubuntu 24.04 LTS — Debian 12 funktioniert genauso
Server — belegte Ports prüfen
# Lauscht schon etwas auf 80, 443 oder 8000?
sudo ss -tulpn | grep -E ':(80|443|8000)\b'
Nginx oder ein eigener Traefik stehen im Weg
Coolify startet seinen eigenen Proxy auf 80 und 443. Läuft dort schon ein Nginx aus einer früheren Einrichtung, bleibt Coolifys Proxy mit address already in use stehen. Vorher sudo systemctl disable --now nginx — oder Coolify auf einen frischen Server setzen.
2
Einmalig pro Server

Coolify installieren

Das Installationsskript richtet alles ein: Docker (falls noch nicht vorhanden), die Coolify-Container, die Datenbank und den Proxy.

Erst lesen, dann ausführen
Ein Skript mit sudo aus dem Netz zu pipen heißt, dem Anbieter vollen Zugriff auf den Server zu geben. Lade es herunter, sieh es dir an und führe es dann aus — der Aufwand ist eine Minute.
Server (per SSH)
# Skript holen, ansehen, dann ausführen
curl -fsSL https://cdn.coollabs.io/coolify/install.sh -o install-coolify.sh
less install-coolify.sh
sudo bash install-coolify.sh

Der Durchlauf dauert je nach Server drei bis fünf Minuten. Am Ende nennt das Skript die Adresse des Dashboards.

Ergebnis
Mehrere Container laufen — prüfbar mit docker ps. Alle Daten von Coolify liegen unter /data/coolify; genau dieser Ordner gehört später ins Backup.
Verwandte Anleitung
Wie Docker von Hand eingerichtet wird und was es mit der UFW-Falle auf sich hat, steht in Docker einrichten & pro Repository integrieren.
3
Einmalig pro Server

Firewall setzen — und das Dashboard nicht öffnen

Nach außen gehören nur die Ports auf, über die Besucher deine Anwendungen erreichen. Das Dashboard auf 8000 gehört nicht dazu.

Server — UFW
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status numbered

# Port 8000 bleibt zu — falls schon geöffnet, Regel wieder entfernen
sudo ufw delete allow 8000/tcp

Ans Dashboard kommst du trotzdem: ein SSH-Tunnel leitet den Port auf deinen eigenen Rechner um. Danach ist Coolify unter http://localhost:8000 erreichbar, aber für sonst niemanden im Netz.

Terminal (lokal)
# Tunnel offen halten, solange du im Dashboard arbeitest
ssh -L 8000:localhost:8000 deploy@203.0.113.10
Ein offenes Dashboard ist ein offener Server
Wer Coolify bedienen kann, kann Container starten, Umgebungsvariablen lesen und ein Terminal öffnen. Das Dashboard über http://<IP>:8000 ungeschützt im Netz stehen zu lassen — auch nur „kurz zum Einrichten" — ist die riskanteste Abkürzung dieser Anleitung.
4
Einmalig pro Server

Admin-Konto anlegen und Registrierung schließen

Beim ersten Aufruf über den Tunnel zeigt Coolify ein Registrierungsformular. Das erste angelegte Konto wird automatisch Administrator.

  • E-Mail und ein langes, einzigartiges Passwort setzen — am besten aus dem Passwortmanager
  • Danach sofort: Settings → Advanced, Schalter Registration allowed ausschalten
  • Optional, aber empfohlen: unter dem eigenen Profil Two-Factor Authentication aktivieren
Das Zeitfenster zwischen Installation und Registrierung
Solange kein Konto existiert und die Registrierung offen ist, wird der Erste, der das Formular findet, Administrator deiner Instanz. Deshalb: Konto direkt nach der Installation anlegen und die Registrierung im selben Zug schließen.
5
Einmalig pro Server

Dashboard hinter eine eigene Domain legen

Auf Dauer ist der SSH-Tunnel unbequem. Gib dem Dashboard stattdessen eine eigene Subdomain mit HTTPS — dann läuft es über Port 443 durch den Proxy, und 8000 bleibt geschlossen.

  • A-Record für coolify.example.de auf die Server-IP setzen und die Auflösung prüfen
  • Im Dashboard unter Settings → General das Feld Instance Domain auf https://coolify.example.de setzen
  • Speichern — Coolify holt das Zertifikat und leitet sich selbst auf die neue Adresse um
Verwandte Anleitung
Zone, Nameserver, Records und die Prüfung mit dig stehen Schritt für Schritt in Domain einrichten & per HTTPS ausliefern.
Erst DNS, dann Domain eintragen
Zeigt der Record noch nicht auf den Server, scheitert die Zertifikatsausstellung — und das Dashboard ist unter der neuen Adresse nicht erreichbar. Der SSH-Tunnel aus Schritt 3 bleibt in dem Fall dein Rückweg.
6
Einmalig pro Server

GitHub anbinden

Damit Coolify deine Repositories klonen und auf Pushes reagieren kann, legst du eine GitHub App an. Coolify führt dich durch den Vorgang.

  • Sources → + Add → GitHub App
  • Name vergeben, Register now — GitHub öffnet sich mit vorausgefüllten Rechten
  • Nach dem Anlegen Install und die Repositories auswählen, auf die Coolify zugreifen darf
GitHub App statt Deploy-Key
Coolify kann Repos auch per Deploy-Key klonen. Die GitHub App ist aber der bessere Weg: sie bringt die Webhooks für Auto-Deploy gleich mit, lässt sich pro Repository freigeben und mit einem Klick wieder entziehen.
Nur die nötigen Repos freigeben
Bei der Installation Only select repositories wählen. „All repositories" gibt einer Anwendung auf deinem Server Lesezugriff auf dein gesamtes GitHub-Konto.
7
Pro App

Projekt anlegen und Anwendung hinzufügen

Coolify sortiert alles in Projekte; jedes Projekt hat mindestens ein Environment (standardmäßig production). Darin liegen die einzelnen Ressourcen.

  • Projects → + Add, Namen wie den des Repos vergeben
  • Im Environment + New Resource → Application → Private Repository (with GitHub App)
  • Die in Schritt 6 angelegte Source wählen, dann Repository und Branch (meist main)
Ein zweites Environment für Staging
Willst du denselben Code aus einem anderen Branch testen, lege im selben Projekt ein Environment staging an und hänge dort eine zweite Anwendung mit Branch develop und eigener Subdomain ein.
8
Pro App

Build-Pack wählen und Port setzen

Das Build-Pack entscheidet, wie aus dem Repository ein Container wird:

  • Dockerfile — dein Repo bringt ein Dockerfile mit. Der ehrlichste Weg: identisch lokal und auf dem Server.
  • Docker Compose — mehrere Dienste aus einer compose.yaml, etwa App und Datenbank zusammen.
  • Nixpacks — kein Dockerfile nötig, Coolify erkennt die Sprache selbst. Bequem für einen schnellen Start, weniger vorhersagbar.

Unter Configuration → General gehören außerdem hinein:

  • Ports Exposes — der Port, auf dem im Container gelauscht wird, z. B. 3000
  • Base Directory — bei einem Monorepo der Unterordner, z. B. /apps/web
  • Build Command / Start Command — nur nötig, wenn sie vom Standard abweichen
Die Anwendung muss auf 0.0.0.0 lauschen
Bindet sie sich im Container an 127.0.0.1, erreicht der Proxy sie nicht — der Aufruf endet in einem 502 Bad Gateway, obwohl der Container läuft. Das ist mit Abstand der häufigste Stolperstein.
Verwandte Anleitung
Wie ein tragfähiges Dockerfile, eine .dockerignore und eine compose.yaml aussehen, steht in Docker einrichten & pro Repository integrieren.
9
Pro App

Umgebungsvariablen und Secrets pflegen

Im Reiter Environment Variables trägst du ein, was nicht ins Repository gehört. Der Unterschied zwischen den beiden Arten ist wichtig:

  • Runtime (Standard) — steht dem laufenden Container zur Verfügung. Datenbank-URLs, API-Schlüssel, Tokens.
  • Build Time — muss zusätzlich angehakt werden. Nötig für alles, was schon beim Bauen eingesetzt wird, etwa NEXT_PUBLIC_* oder VITE_*.
Environment Variables (Beispiel)
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://app:geheim@datenbank:5432/app
SESSION_SECRET="per openssl rand -hex 32 erzeugen"
Die .env bleibt draußen
Die echten Werte leben in Coolify, nicht im Repo. Dort gehört nur eine .env.example ohne Geheimnisse hin, und .env in die .gitignore. Was einmal committet wurde, bleibt in der Git-Historie — dann hilft nur noch, das Secret zu wechseln.
Build-Time-Variablen brauchen einen neuen Build
Änderst du eine Runtime-Variable, genügt ein Neustart. Bei Build-Time-Variablen muss die Anwendung neu gebaut werden — sonst steckt im Abbild noch der alte Wert.
10
Pro App

Domain zuweisen und erstmals ausrollen

Unter Configuration → General → Domains die vollständige URL eintragen — mit https://, ohne abschließenden Schrägstrich:

Domains
https://app.example.de

Speichern, dann oben rechts auf Deploy. Der Build läuft sichtbar im Log mit.

Ergebnis
Der Status springt auf Running, das Zertifikat ist da, https://app.example.de zeigt deine Anwendung.
Wenn es nicht läuft — in dieser Reihenfolge prüfen
Build bricht ab → das Deployment-Log liest sich wie ein lokales docker build; meist fehlt eine Build-Time-Variable. 502 Bad Gateway → falscher Port oder Bindung an 127.0.0.1. Kein Zertifikat → der DNS-Record zeigt nicht auf den Server, siehe Domain einrichten.
11
Pro App

Auto-Deploy prüfen

Über die GitHub App hat Coolify den Webhook bereits eingerichtet. Unter Configuration → General muss nur Auto Deploy aktiv sein — dann löst jeder Push auf den gewählten Branch ein neues Deployment aus.

Terminal (lokal) — Test
git commit -m "Auto-Deploy testen" --allow-empty
git push origin main
Ergebnis
Wenige Sekunden nach dem Push erscheint unter Deployments ein neuer Eintrag. Damit ist der Kreis geschlossen: Push → Build → Container-Tausch, ohne dass du dich auf dem Server anmeldest.
Passiert nichts?
Im Repository unter Settings → GitHub Apps → Advanced die letzten Webhook-Zustellungen ansehen. Ein roter Eintrag zeigt, ob GitHub Coolify überhaupt erreicht hat — das trennt Netzproblem von Konfigurationsfehler.
12
Pro App

Betrieb: Logs, Rollback, Speicher, Updates

Was du im Alltag brauchst — das meiste davon direkt im Dashboard:

  • Logs — laufende Ausgabe des Containers, ohne SSH
  • Terminal — Shell im Container, praktisch für Migrationen
  • Deployments → Rollback — zurück auf ein früheres Abbild, wenn ein Deploy etwas kaputt macht
  • Persistent Storage — ein Volume für Uploads oder eine SQLite-Datei; ohne das ist beim nächsten Deploy alles weg
Container sind vergänglich
Jedes Deployment ersetzt den Container vollständig. Alles, was nicht in einem Volume oder einer Datenbank liegt — hochgeladene Dateien, generierte Bilder, eine SQLite-Datei im Projektordner — ist danach verschwunden. Volumes vor dem ersten produktiven Einsatz anlegen.

Coolify selbst aktualisierst du unter Settings → Update. Vorher lohnt ein Blick auf das Datenverzeichnis:

Server — Zustand und Platz
docker ps                        # Laufen alle Container?
docker system df                 # Platzverbrauch von Abbildern und Volumes
sudo du -sh /data/coolify         # Coolifys Daten — das gehört ins Backup
