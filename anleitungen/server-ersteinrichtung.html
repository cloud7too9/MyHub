Server-Erst-Einrichtung & Absicherung

⏱ ca. 45 Min Aktualisiert 05.08.2026 Ubuntu 24.04 LTS · Hetzner Cloud

Vom frisch erstellten Server zur abgesicherten Basis: eigenes Schlüsselpaar je Gerät, drei Rollen statt eines Alleskönners, SSH nur noch per Schlüssel, root gesperrt, Firewall und Brute-Force-Schutz aktiv.

Reihenfolge zählt
Die Schritte 1–6 laufen bewusst vor dem Absichern in Schritt 7. Wer den Passwort-Login sperrt, bevor jeder Nutzer und jedes Gerät seinen Schlüssel hat, sperrt sich selbst aus.
Zwei Ausgangslagen
Weg A: Beim Erstellen des Servers war dein öffentlicher Schlüssel schon hinterlegt. Weg B: Der Server kennt nur ein Passwort. Wo sich die Wege unterscheiden, steht ein Umschalter im Schritt — die Wahl gilt dann für die ganze Seite.

Die einmaligen Server-Schritte sind ausgeblendet — sichtbar bleibt der Weg, den du für jeden weiteren Nutzer und jedes weitere Gerät gehst.

1
Pro Gerät

Lokales Schlüsselpaar prüfen — sonst anlegen

Der Schlüssel entsteht auf deinem Gerät, nicht auf dem Server. Der private Teil bleibt hier und verlässt das Gerät nie; nur der öffentliche wandert auf den Server. Unter Windows laufen dieselben Befehle in der PowerShell, das Verzeichnis heißt dort C:\Users\<du>\.ssh.

Prüfen
Terminal (lokal)
ls -l ~/.ssh/id_ed25519.pub

Soll: eine Datei. Dann hast du bereits ein Paar und lässt es, wie es ist.

Fehlt
Terminal (lokal)
# Verzeichnis anlegen, falls es das noch nicht gibt
mkdir -p ~/.ssh && chmod 700 ~/.ssh

# Der Kommentar hinter -C benennt das Gerät — nicht die Person
ssh-keygen -t ed25519 -C "max@laptop"

Danach liegen zwei Dateien nebeneinander: id_ed25519 (privat, bleibt hier) und id_ed25519.pub (öffentlich, darf überall hin).

Warum der Kommentar zählt
Er steht später Zeichen für Zeichen in der authorized_keys auf dem Server. Ohne ihn stehen dort mehrere gleich aussehende Zeilen, und du weißt nicht mehr, welche zum verlorenen Tablet gehört.
Passphrase: ja
Der private Schlüssel ist eine Datei — ohne Passphrase genügt ein kopierter Ordner, um dein Konto zu übernehmen. Mit ssh-agent tippst du sie einmal je Sitzung, nicht bei jedem Login.

Weg A oder B? Auf Weg B ist dieser Schritt zwingend — ohne öffentlichen Schlüssel gibt es in Schritt 5 nichts zu hinterlegen. Auf Weg A ist er längst erledigt, sonst hättest du den Server nicht mit Schlüssel erstellen können.

2
Einmalig pro Server

Als root einloggen und System aktualisieren

Der erste Login läuft je nach Ausgangslage anders. Erste Amtshandlung ist danach in beiden Fällen dieselbe: alles auf aktuellen Stand bringen.

Beim Erstellen des Servers hast du deinen öffentlichen Schlüssel hinterlegt — der Login läuft ohne Passwort. Bei Hetzner-Images ist der Passwort-Login dann meist von vornherein aus.

Terminal (lokal)
ssh root@<SERVER-IP>

Der Server kennt nur ein Passwort; bei Hetzner kommt es per Mail. Beim ersten Login verlangt er sofort ein neues — leg es im Passwortspeicher ab: Bis Schritt 7 ist es dein einziger Zugang, und danach bleibt es der Schlüssel zur Notfall-Konsole des Anbieters.

Terminal (lokal)
ssh root@<SERVER-IP>

# Der Server fragt zuerst das Passwort aus der Mail ab und verlangt
# dann sofort ein neues. Erst danach steht die Sitzung.

Bis Schritt 7 bleibt der Passwort-Login offen — auf diesem Weg unvermeidlich, denn du brauchst ihn in Schritt 5 selbst. Genau deshalb sollte Schritt 7 heute passieren und nicht nächste Woche.

Server
apt update && apt full-upgrade -y

# Neustart nötig? Datei existiert nur, wenn ja
[ -f /var/run/reboot-required ] && reboot
3
Einmalig pro Server

Hostname und Zeitzone ansehen

Ansehen ist Pflicht, Ändern nicht: Viele Anbieter setzen beides schon beim Erstellen. Beim Lesen von Logs ist es später viel wert — Zeitstempel in lokaler Zeit und ein Name, den du wiedererkennst.

Prüfen
Server
hostnamectl
timedatectl

Soll: Static hostname ist ein Name, den du wiedererkennst, Time zone passt zu der Zeit, in der du Logs liest.

Stimmt nicht
Server (als root)
hostnamectl set-hostname web01
timedatectl set-timezone Europe/Berlin

# Der Name gehört zusätzlich in die Hosts-Datei — sonst hängt sudo
# bei jedem Aufruf kurz an der Namensauflösung
grep -q web01 /etc/hosts || echo "127.0.1.1 web01" >> /etc/hosts
4
Pro Nutzer

Identität und Rechte

Ab jetzt arbeitest du nicht mehr als root. Ein Konto steht für eine Person oder eine Aufgabe — und nicht jedes Konto darf alles. Wer über einen Login hereinkommt, soll genau das können, wofür er da ist.

Server (als root)
# 1) Admin — darf über sudo alles, das Passwort ist die Bremse davor
adduser max
usermod -aG sudo max

# 2) Eingeschränkter Nutzer — kein sudo, nur die eigenen Dateien
adduser lena

# 3) Dienst-Nutzer — kein Passwort, kein sudo, nur Schlüssel-Login
adduser --disabled-password --gecos "" deploy
Zwei Sorten Dienst-Nutzer
--disabled-password heißt: Es gibt kein Passwort, mit dem man sich anmelden könnte — der Zugang läuft ausschließlich über den hinterlegten Schlüssel. Wer gar keinen Login will (ein reiner Datei-Besitzer für einen Dienst), setzt zusätzlich --shell /usr/sbin/nologin. Dann laufen aber auch Deploy-Befehle über SSH nicht mehr.

Passwort wofür? Der SSH-Login läuft ab Schritt 7 rein über den Schlüssel. Das Passwort des Admins brauchst du nur noch für sudo auf dem Server selbst — das ist die gewünschte Bremse vor Systemänderungen.

Prüfen
Server
id max
id lena
id deploy

Soll: sudo taucht nur bei max in der Gruppenliste auf.

Stimmt nicht
Server (als root)
# Rechte geben …
usermod -aG sudo max

# … oder wieder wegnehmen
deluser lena sudo

Gruppenwechsel greifen erst bei der nächsten Anmeldung — bestehende Sitzungen des Nutzers vorher beenden.

Zwischenstufe: gezielte sudo-Rechte. Zwischen „alles“ und „nichts“ liegt der nützlichste Fall: Ein Nutzer darf genau die Befehle, die zu seiner Aufgabe gehören. Das gehört in eine eigene Datei unter /etc/sudoers.d/ — nie in die sudoers selbst.

/etc/sudoers.d/50-lena-neustart
# Genau zwei Befehle, mit vollem Pfad. Ohne Pfad ließe sich ein
# gleichnamiges Programm im eigenen Verzeichnis unterschieben.
lena ALL=(root) /usr/bin/systemctl restart meineapp, /usr/bin/systemctl status meineapp
Server — anlegen und prüfen
# visudo statt nano: prüft beim Speichern und legt 0440 an.
# Ein Syntaxfehler in sudoers.d sperrt sonst jedes sudo im System.
sudo visudo -f /etc/sudoers.d/50-lena-neustart

# Alle Regeln zusammen gegenlesen — muss "parsed OK" melden
sudo visudo -c

# Was darf lena wirklich?
sudo -l -U lena
Der Dateiname darf keinen Punkt enthalten
sudoers.d überliest jede Datei mit . oder ~ im Namen — 50-lena.conf wirkt also nie, ohne dass irgendwo eine Fehlermeldung stünde. Und: Ein Editor oder eine Shell in der Befehlsliste hebt die ganze Beschränkung auf, denn aus beidem heraus lässt sich alles Weitere starten.
Die Gruppe docker hebelt alles aus
Wer in der Gruppe docker ist, kann sich einen Container mit dem Wurzelverzeichnis des Servers geben — und ist damit faktisch root, ohne Passwortabfrage und ohne Eintrag in den sudo-Logs. Jede Abstufung darüber ist dann Zierde. Nimm in die Gruppe nur auf, wem du auch sudo ohne Passwort geben würdest; für Deploys lieber gezielte Rechte auf die Compose-Befehle.

Ein Nutzer, mehrere Geräte. Das Konto steht für die Person, nicht für den Laptop. Kommt ein zweites Gerät dazu, entsteht kein zweites Konto — es kommt eine weitere Schlüsselzeile in dieselbe Datei des Nutzers. Der Vorteil zeigt sich beim Verlust: Ein Gerät fliegt raus, das Konto und alle anderen Geräte bleiben. Die Handgriffe dazu stehen in Schritt 5.

5
Pro Nutzer und Gerät

Schlüssel hinterlegen

Alle Handgriffe rund um Schlüssel stehen hier an einer Stelle — damit du diesen Schritt später allein aufschlagen kannst, wenn ein neues Gerät, ein neuer Kollege oder ein Deploy-Zugang dazukommt.

Der erste Schlüssel für den Admin kommt je nach Ausgangslage von einer anderen Seite:

Dein Schlüssel liegt bereits auf dem Server — allerdings bei root. Er wird zum neuen Konto übernommen, und zwar nur der öffentliche Teil.

Server (als root)
# Verzeichnis mit den richtigen Rechten und Besitzern anlegen
install -d -m 700 -o max -g max /home/max/.ssh

# Nur beim ersten Mal! install überschreibt die Zieldatei —
# weitere Geräte werden weiter unten angehängt, nicht so übernommen.
install -m 600 -o max -g max /root/.ssh/authorized_keys /home/max/.ssh/authorized_keys
Nicht das ganze Verzeichnis kopieren
Der verbreitete Einzeiler rsync --archive --chown=max:max ~/.ssh /home/max nimmt alles mit, was in /root/.ssh liegt — auch einen dort abgelegten privaten Schlüssel. Die authorized_keys allein genügt.

Auf dem Server liegt noch kein Schlüssel. Er wird von deinem Gerät aus hochgeschoben — mit dem Passwort, das du in Schritt 4 für max vergeben hast.

Terminal (lokal)
ssh-copy-id max@<SERVER-IP>

Ohne ssh-copy-id (etwa in der Windows-PowerShell) geht es in einem Befehl — er legt Verzeichnis und Rechte gleich mit an:

PowerShell (lokal)
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh max@<SERVER-IP> "install -d -m 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
Braucht noch den Passwort-Login
Beide Wege melden sich mit Passwort an. Sie funktionieren also nur vor Schritt 7. Wer erst härtet und dann Schlüssel verteilen will, steht vor einer verschlossenen Tür — genau die Falle, die diese Anleitung sonst überall vermeidet.

Für jeden weiteren Nutzer. Dessen öffentlicher Schlüssel entsteht auf dessen Gerät (Schritt 1) und wird dir als Textzeile geschickt. Du legst sie ab — der private Schlüssel bleibt dabei immer beim Besitzer.

Server (als root)
install -d -m 700 -o lena -g lena /home/lena/.ssh

# Die Zeile aus lenas id_ed25519.pub — anhängen, nicht überschreiben
echo "ssh-ed25519 AAAA… lena@laptop" >> /home/lena/.ssh/authorized_keys

chown lena:lena /home/lena/.ssh/authorized_keys
chmod 600 /home/lena/.ssh/authorized_keys

Zweites Gerät desselben Nutzers. Jedes Gerät bekommt ein eigenes Schlüsselpaar nach Schritt 1. Der private Schlüssel wird nie von einem Gerät auf ein anderes kopiert — nur so lässt sich später ein einzelnes Gerät aussperren, ohne allen anderen den Zugang zu nehmen. Angehängt wird die neue Zeile am besten vom Nutzer selbst:

Server (als der Nutzer)
echo "ssh-ed25519 AAAA… max@tablet" >> ~/.ssh/authorized_keys

# Was liegt jetzt drin? Zeigt Fingerabdruck und Kommentar je Zeile
ssh-keygen -lf ~/.ssh/authorized_keys
/home/max/.ssh/authorized_keys — so sieht es aus
# Eine Zeile je Gerät. Der Kommentar am Ende ist die Gerätezuordnung —
# ohne ihn stehen hier mehrere nicht unterscheidbare Zeilen.
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… max@laptop
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… max@tablet
Ein Gerät aussperren
Die eine Zeile mit dem passenden Kommentar aus der authorized_keys löschen — fertig. Alle anderen Geräte des Nutzers bleiben unberührt. Wäre überall derselbe Schlüssel im Einsatz, müsstest du stattdessen jedem alles neu verteilen.
Prüfen
Server
ls -ld /home/max/.ssh
ls -l /home/max/.ssh/authorized_keys

Soll: drwx------ für den Ordner, -rw------- für die Datei, und als Besitzer beide Male der Nutzer selbst — nicht root.

Fehlt oder stimmt nicht
Server (als root)
# Legt das Verzeichnis an, falls es fehlt, und rückt sonst die Rechte gerade
install -d -m 700 -o max -g max /home/max/.ssh

touch /home/max/.ssh/authorized_keys
chown max:max /home/max/.ssh/authorized_keys
chmod 600 /home/max/.ssh/authorized_keys

Zu weite Rechte sind der häufigste stille Fehler: sshd übergeht die Datei dann kommentarlos, und der Login endet mit Permission denied (publickey) — obwohl der Schlüssel richtig dasteht.

Eingeschränkter Schlüssel für den Dienst-Nutzer. Ein Schlüssel kann mehr als nur öffnen: Vorangestellte Optionen legen fest, was mit ihm überhaupt möglich ist. Für einen Deploy-Zugang heißt das — genau ein Befehl, keine Shell, keine Tunnel.

/home/deploy/.ssh/authorized_keys
# restrict schaltet alles ab (Tunnel, Weiterleitungen, Terminal);
# command erzwingt genau dieses Skript, egal was der Aufrufer schickt.
# from nur setzen, wenn die Gegenstelle eine feste IP hat.
restrict,command="/usr/local/bin/deploy.sh" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… deploy@ci
6
Pro Nutzer und Gerät

Alle Rollen testen — auch das, was nicht gehen darf

Der wichtigste Schritt der ganzen Anleitung. Öffne ein zweites Terminal-Fenster; die bestehende Sitzung bleibt als Rettungsleine offen. Beim ersten Durchlauf ist das die root-Sitzung, später die deines Admin-Kontos.

Terminal (neues Fenster) — Admin
ssh max@<SERVER-IP>

# Läuft sudo? Muss "root" ausgeben
sudo whoami
Terminal — eingeschränkter Nutzer
ssh lena@<SERVER-IP>

# NEGATIVTEST — muss scheitern:
# "lena is not in the sudoers file" oder "not allowed to execute"
sudo whoami

# Und das hier muss laufen: genau die freigegebenen Befehle
sudo -l
sudo systemctl status meineapp
Terminal — Dienst-Nutzer
# Mit erzwungenem Befehl kommt nicht "deploy" zurück, sondern
# die Ausgabe von deploy.sh — auch das ist ein bestandener Test
ssh -i ~/.ssh/id_ed25519_deploy deploy@<SERVER-IP> "whoami"
Ein bestandener Negativtest zählt wie ein bestandener Login
Klappt der Login und scheitert sudo nicht, ist die Abstufung aus Schritt 4 nur eine Absicht geblieben. Prüfe dann die Gruppen mit id lena und die Regeln mit sudo -l -U lena. Erst weiter, wenn jede Rolle genau so reagiert wie geplant — die alte Sitzung ist noch offen und rettet dich.

Kommt ein weiteres Gerät dazu, wird dieser Test von diesem Gerät aus wiederholt. ssh -v max@<SERVER-IP> zeigt in der Ausgabe, welcher Schlüssel angenommen wurde.

7
Einmalig pro Server

SSH härten: root-Login und Passwörter sperren

Jetzt wird zugemacht. Vorher steht aber ein Tor: Mit drei Rollen und mehreren Geräten ist der Passwort-Login für mehr Zugänge die letzte offene Tür, als einem beim Setzen des Hakens bewusst ist.

Tor davor: Hat jeder seinen Schlüssel?
Server
# Zählt die hinterlegten Schlüssel je Konto — eine Zeile ist ein Gerät
for d in /root/ /home/*/; do
  n=$(grep -c '^ssh-' "$d.ssh/authorized_keys" 2>/dev/null)
  echo "$d ${n:-0}"
done

Soll: Jedes Konto, das sich später anmelden können muss, steht mit mindestens 1 da — und für jedes Gerät eine Zeile mehr. Der Dienst-Nutzer zählt mit.

Steht irgendwo 0

Zurück zu Schritt 5 und den fehlenden Schlüssel hinterlegen — solange der Passwort-Login noch steht, ist das eine Minute Arbeit. Danach wäre es ein Fall für die Notfall-Konsole des Anbieters. Konten, die sich nie anmelden sollen (etwa Systemkonten), dürfen selbstverständlich bei 0 bleiben.

Die Einstellungen kommen in eine eigene Datei unter /etc/ssh/sshd_config.d/ — nicht in die sshd_config selbst.

Der Dateiname entscheidet
Bei SSH gilt: der erste gefundene Wert gewinnt. Cloud-Images legen oft 50-cloud-init.conf mit PasswordAuthentication yes an. Eine Datei namens 99-… wird später gelesen und bleibt wirkungslos — deshalb hier 00-haertung.conf.
Server — vorhandene Schnipsel ansehen
ls -l /etc/ssh/sshd_config.d/
/etc/ssh/sshd_config.d/00-haertung.conf
# Nur noch Schlüssel-Anmeldung, kein root, keine Passwörter
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
X11Forwarding no
MaxAuthTries 3
Server — anlegen, prüfen, neu laden
sudo nano /etc/ssh/sshd_config.d/00-haertung.conf

# Syntax prüfen — muss stumm bleiben
sudo sshd -t

sudo systemctl restart ssh
Prüfen
Server — tatsächlich wirksame Werte
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|kbdinteractive'

Soll: dreimal no. Das ist die einzige Ausgabe, die zählt — was in deiner Datei steht, kann von einem früher gelesenen Schnipsel überstimmt sein.

Steht dort yes
Server — wer setzt den Wert?
# Zeigt Datei und Zeile jedes Vorkommens
sudo grep -rniE 'passwordauthentication|permitrootlogin' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/

# Den früher gelesenen Wert anpassen (meist 50-cloud-init.conf),
# danach erneut prüfen
sudo nano /etc/ssh/sshd_config.d/50-cloud-init.conf
sudo systemctl restart ssh
Socket-Aktivierung
Ubuntu startet sshd seit 22.10 pro Verbindung über ssh.socket. Für Optionen wie diese reicht der Neustart oben — nur beim Port muss zusätzlich der Socket angefasst werden (Schritt 11).
Noch ein Tor: AllowUsers
Mit AllowUsers max lena deploy kommt gar nicht erst zur Schlüsselprüfung, wer nicht in der Liste steht. Wirksam, aber mit Merkposten: Jedes neue Konto muss hier nachgetragen werden, sonst kommt es trotz gültigem Schlüssel nicht herein. Nimm die Zeile nur auf, wenn du sie in Schritt 4 mitpflegst.

Test vor dem Schließen der root-Sitzung: ein drittes Fenster öffnen. ssh max@<SERVER-IP> muss laufen, ssh root@<SERVER-IP> muss abgewiesen werden.

8
Einmalig pro Server

Firewall einrichten (UFW)

Alles dicht, außer was du ausdrücklich öffnest. Zuerst SSH freigeben, dann einschalten — sonst kappt die Firewall die laufende Sitzung.

Server
sudo ufw default deny incoming
sudo ufw default allow outgoing

# SSH zuerst! Danach erst aktivieren
sudo ufw allow OpenSSH

# Bei Webserver zusätzlich:
# sudo ufw allow 80,443/tcp

sudo ufw enable
Prüfen
Server
sudo ufw status verbose

Soll: Status: active, deny (incoming) als Vorgabe und eine ALLOW-Zeile für OpenSSH.

SSH fehlt in der Liste
Server
sudo ufw allow OpenSSH
sudo ufw reload

Kommst du gar nicht mehr rein, hilft nur die Konsole im Cloud-Panel des Anbieters — sie hängt nicht an SSH. Dort ufw disable, Regel nachtragen, wieder einschalten.

Zweite Ebene
Die Cloud-Firewall bei Hetzner arbeitet vor dem Server und kostet nichts. Beide zu nutzen ist sinnvoll — aber dann Regeln an beiden Stellen pflegen, sonst suchst du Fehler an der falschen Stelle.
9
Einmalig pro Server

Brute-Force-Schutz mit fail2ban

fail2ban liest die Logs mit und sperrt IPs, die es wiederholt falsch versuchen. Eigene Einstellungen kommen in jail.local — jail.conf wird bei Updates überschrieben.

Server
sudo apt install fail2ban -y
sudo nano /etc/fail2ban/jail.local
/etc/fail2ban/jail.local
[DEFAULT]
# Ab Werk stehen hier nur die lokalen Adressen — die schützen dich
# nicht. Deine eigene feste IP gehört ausdrücklich dazugeschrieben.
ignoreip = 127.0.0.1/8 ::1 203.0.113.5

[sshd]
enabled  = true
# Journal statt Logdatei — läuft unabhängig von rsyslog
backend  = systemd
maxretry = 3
findtime = 10m
bantime  = 1h
Wechselnde IP zu Hause?
Dann trag dort nichts ein — eine fremde IP freizustellen ist schlechter, als sich selbst aussperren zu können. Der Rettungsweg ist die Konsole im Cloud-Panel, und entsperren lässt sich jederzeit von Hand.
Server — starten
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban
Prüfen
Server
sudo fail2ban-client status sshd

Soll: Die Jail antwortet mit Zählern; Currently banned zeigt die gesperrten IPs.

Keine Jail — oder du sitzt selbst in der Sperre
Server
# Warum startet die Jail nicht? Meist ein Tippfehler in jail.local
sudo journalctl -u fail2ban -n 30 --no-pager

# Eigene IP wieder freigeben (auch aus der Anbieter-Konsole heraus)
sudo fail2ban-client set sshd unbanip 203.0.113.5
Einordnung
Der große Sicherheitsgewinn kam schon in Schritt 7 — ohne Passwort-Login läuft ein Rateangriff ins Leere. fail2ban hält zusätzlich die Logs sauber und bremst Dauerscanner aus.
10
Einmalig pro Server

Automatische Sicherheitsupdates

Damit der Server nicht dadurch unsicher wird, dass du wochenlang nicht hinschaust.

Server
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure --priority=low unattended-upgrades
Prüfen
Server
cat /etc/apt/apt.conf.d/20auto-upgrades

# Trockenlauf — zeigt, was tatsächlich gezogen würde
sudo unattended-upgrades --dry-run --debug

Soll: beide Werte stehen auf "1".

Datei fehlt oder steht auf 0
/etc/apt/apt.conf.d/20auto-upgrades
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
Server — anlegen und übernehmen
sudo nano /etc/apt/apt.conf.d/20auto-upgrades
sudo systemctl restart unattended-upgrades
11
Optional

SSH-Port verlegen

Bringt keine echte Sicherheit, aber deutlich weniger Rauschen in den Logs. Unter Ubuntu 24.04 reicht der Eintrag in der Konfiguration nicht — der Socket lauscht sonst weiter auf 22.

Server — Port in der SSH-Konfiguration
echo "Port 2222" | sudo tee -a /etc/ssh/sshd_config.d/00-haertung.conf
Server — Socket-Override anlegen
sudo systemctl edit ssh.socket
Inhalt des Overrides
[Socket]
# Leere Zeile löscht den Standard-Port 22
ListenStream=
ListenStream=2222
Server — Firewall zuerst, dann übernehmen
sudo ufw allow 2222/tcp

sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
Prüfen
Server
sudo ss -tuln | grep 2222

Soll: eine Zeile mit :2222 im Zustand LISTEN.

Keine Ausgabe — oder weiterhin 22
Server
# Ist der Override wirklich angekommen?
systemctl cat ssh.socket

# Fehlt die leere ListenStream-Zeile, lauscht er auf beiden Ports
sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
Sitzung offen lassen
Erst mit ssh -p 2222 max@<SERVER-IP> aus einem zweiten Fenster testen. Klappt es, kann die alte Regel weg: sudo ufw delete allow OpenSSH. Klappt es nicht, hilft die Konsole im Hetzner-Cloud-Panel.
