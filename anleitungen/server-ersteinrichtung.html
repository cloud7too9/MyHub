Server-Erst-Einrichtung & Absicherung

⏱ ca. 30 Min Aktualisiert 02.08.2026 Ubuntu 24.04 LTS · Hetzner Cloud

Vom frisch erstellten Server zur abgesicherten Basis: eigener Benutzer, SSH nur noch per Schlüssel, root gesperrt, Firewall und Brute-Force-Schutz aktiv.

Reihenfolge zählt
Die Schritte 1–5 laufen bewusst vor dem Absichern in Schritt 6. Wer root sperrt, bevor der neue Zugang getestet ist, sperrt sich selbst aus.

Die einmaligen Schritte sind ausgeblendet — sichtbar bleibt der Weg, den du jedes Mal gehst.

1
Einmalig pro Server

Als root einloggen und System aktualisieren

Beim Erstellen des Servers hast du deinen SSH-Schlüssel hinterlegt — damit kommst du direkt als root rein. Erste Amtshandlung: alles auf aktuellen Stand bringen.

Terminal (lokal)
ssh root@<SERVER-IP>
Server
apt update && apt full-upgrade -y

# Neustart nötig? Datei existiert nur, wenn ja
[ -f /var/run/reboot-required ] && reboot
2
Einmalig pro Server

Hostname und Zeitzone setzen

Kleinigkeit, die später beim Lesen von Logs viel wert ist — Zeitstempel in lokaler Zeit und ein Name, den du wiedererkennst.

Server
hostnamectl set-hostname web01
timedatectl set-timezone Europe/Berlin

# Hostname zusätzlich in der Hosts-Datei ergänzen
echo "127.0.1.1 web01" >> /etc/hosts
3
Einmalig pro Server

Benutzer anlegen und sudo-Rechte geben

Ab jetzt arbeitest du nicht mehr als root. Der neue Benutzer bekommt über die Gruppe sudo die Rechte, die er punktuell braucht.

Server (als root)
# Fragt nach einem Passwort — vergib ein starkes, du brauchst es für sudo
adduser max

# In die sudo-Gruppe aufnehmen
usermod -aG sudo max
Warum ein Passwort
Der SSH-Login läuft gleich rein über den Schlüssel. Das Passwort brauchst du nur noch für sudo auf dem Server selbst — das ist die gewünschte Bremse vor Systemänderungen.
4
Einmalig pro Server

SSH-Schlüssel für den neuen Benutzer hinterlegen

Der Schlüssel liegt bisher nur bei root. Kopiere das komplette .ssh-Verzeichnis inklusive Besitzrechten zum neuen Benutzer.

Server (als root)
rsync --archive --chown=max:max ~/.ssh /home/max
Ergebnis
/home/max/.ssh/authorized_keys enthält denselben Schlüssel wie bei root, gehört aber max. Rechte prüfen: Ordner 700, Datei 600.
Server — Rechte kontrollieren
ls -ld /home/max/.ssh
ls -l /home/max/.ssh/authorized_keys
5
Einmalig pro Server

Neuen Zugang testen — root-Sitzung offen lassen

Das ist der wichtigste Schritt der ganzen Anleitung. Öffne ein zweites Terminal-Fenster und logge dich als neuer Benutzer ein. Die root-Sitzung bleibt als Rettungsleine offen.

Terminal (neues Fenster)
ssh max@<SERVER-IP>

# Läuft sudo? Muss "root" ausgeben
sudo whoami
Erst weiter, wenn beides klappt
Login per Schlüssel und sudo whoami müssen funktionieren. Sonst zurück zu Schritt 4 — die root-Sitzung ist noch offen und rettet dich.
6
Einmalig pro Server

SSH härten: root-Login und Passwörter sperren

Jetzt wird zugemacht. Die Einstellungen kommen in eine eigene Datei unter /etc/ssh/sshd_config.d/ — nicht in die sshd_config selbst.

Der Dateiname entscheidet
Bei SSH gilt: der erste gefundene Wert gewinnt. Cloud-Images legen oft 50-cloud-init.conf mit PasswordAuthentication yes an. Eine Datei namens 99-… wird später gelesen und bleibt wirkungslos — deshalb hier 00-haertung.conf.
Server — vorhandene Schnipsel ansehen
ls -l /etc/ssh/sshd_config.d/
/etc/ssh/sshd_config.d/00-haertung.conf
# Nur noch Schlüssel-Anmeldung, kein root, keine Passwörter
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
X11Forwarding no
MaxAuthTries 3
Server — anlegen, prüfen, neu laden
sudo nano /etc/ssh/sshd_config.d/00-haertung.conf

# Syntax prüfen — muss stumm bleiben
sudo sshd -t

# Tatsächlich wirksame Werte anzeigen (entscheidend!)
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|kbdinteractive'

sudo systemctl restart ssh
Soll-Ausgabe
Dreimal no. Steht dort passwordauthentication yes, greift ein anderer Schnipsel zuerst — dann den Wert in 50-cloud-init.conf anpassen oder die Datei entfernen.
Socket-Aktivierung
Ubuntu startet sshd seit 22.10 pro Verbindung über ssh.socket. Für Optionen wie diese reicht der Neustart oben — nur beim Port muss zusätzlich der Socket angefasst werden (Schritt 10).

Test vor dem Schließen der root-Sitzung: ein drittes Fenster öffnen, ssh max@<SERVER-IP> muss laufen, ssh root@<SERVER-IP> muss abgewiesen werden.

7
Einmalig pro Server

Firewall einrichten (UFW)

Alles dicht, außer was du ausdrücklich öffnest. Zuerst SSH freigeben, dann einschalten — sonst kappt die Firewall die laufende Sitzung.

Server
sudo ufw default deny incoming
sudo ufw default allow outgoing

# SSH zuerst! Danach erst aktivieren
sudo ufw allow OpenSSH

# Bei Webserver zusätzlich:
# sudo ufw allow 80,443/tcp

sudo ufw enable
sudo ufw status verbose
Zweite Ebene
Die Cloud-Firewall bei Hetzner arbeitet vor dem Server und kostet nichts. Beide zu nutzen ist sinnvoll — aber dann Regeln an beiden Stellen pflegen, sonst suchst du Fehler an der falschen Stelle.
8
Einmalig pro Server

Brute-Force-Schutz mit fail2ban

fail2ban liest die Logs mit und sperrt IPs, die es wiederholt falsch versuchen. Eigene Einstellungen kommen in jail.local — jail.conf wird bei Updates überschrieben.

Server
sudo apt install fail2ban -y
sudo nano /etc/fail2ban/jail.local
/etc/fail2ban/jail.local
[DEFAULT]
# Eigene IP nie sperren (mehrere durch Leerzeichen trennen)
ignoreip = 127.0.0.1/8 ::1

[sshd]
enabled  = true
# Journal statt Logdatei — läuft unabhängig von rsyslog
backend  = systemd
maxretry = 3
findtime = 10m
bantime  = 1h
Server — starten und kontrollieren
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban

# Läuft die Jail? Zeigt auch gesperrte IPs
sudo fail2ban-client status sshd
Einordnung
Der große Sicherheitsgewinn kam schon in Schritt 6 — ohne Passwort-Login läuft ein Rateangriff ins Leere. fail2ban hält zusätzlich die Logs sauber und bremst Dauerscanner aus.
9
Einmalig pro Server

Automatische Sicherheitsupdates

Damit der Server nicht dadurch unsicher wird, dass du wochenlang nicht hinschaust.

Server
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure --priority=low unattended-upgrades

# Kontrolle: beide Werte müssen "1" sein
cat /etc/apt/apt.conf.d/20auto-upgrades

# Trockenlauf
sudo unattended-upgrades --dry-run --debug
10
Optional

Optional: SSH-Port verlegen

Bringt keine echte Sicherheit, aber deutlich weniger Rauschen in den Logs. Unter Ubuntu 24.04 reicht der Eintrag in der Konfiguration nicht — der Socket lauscht sonst weiter auf 22.

Server — Port in der SSH-Konfiguration
echo "Port 2222" | sudo tee -a /etc/ssh/sshd_config.d/00-haertung.conf
Server — Socket-Override anlegen
sudo systemctl edit ssh.socket
Inhalt des Overrides
[Socket]
# Leere Zeile löscht den Standard-Port 22
ListenStream=
ListenStream=2222
Server — Firewall zuerst, dann übernehmen
sudo ufw allow 2222/tcp

sudo systemctl daemon-reload
sudo systemctl restart ssh.socket

# Lauscht er wirklich auf 2222?
sudo ss -tuln | grep 2222
Sitzung offen lassen
Erst mit ssh -p 2222 max@<SERVER-IP> aus einem zweiten Fenster testen. Klappt es, kann die alte Regel weg: sudo ufw delete allow OpenSSH. Klappt es nicht, hilft die Konsole im Hetzner-Cloud-Panel.
