Domain einrichten & per HTTPS ausliefern

⏱ ca. 30 Min Aktualisiert 04.08.2026 Hetzner DNS · anbieterneutral

Von der gekauften Domain bis zum grünen Schloss: Zone anlegen, Nameserver umstellen, Records setzen — und das Zertifikat entweder von Coolify oder von Certbot holen lassen.

Die einmaligen Schritte sind ausgeblendet — sichtbar bleibt der Weg, den du für jedes neue Projekt gehst.

1
Einmalig pro Server

IP-Adressen des Servers ermitteln

Ein DNS-Eintrag ist am Ende nichts anderes als „Name → IP". Also brauchst du zuerst die beiden Adressen deines Hetzner-Servers. Sie stehen in der Hetzner-Cloud-Konsole beim Server, oder du fragst sie direkt auf dem Server ab.

Server (per SSH)
# Öffentliche IPv4 des Servers
curl -4 https://ifconfig.me

# Öffentliche IPv6 — leer oder Fehler heißt: keine nutzbare IPv6
curl -6 https://ifconfig.me
IPv6 nur eintragen, wenn sie wirklich antwortet
Ein AAAA-Record auf eine IPv6, unter der nichts lauscht, führt zu sporadisch nicht erreichbaren Seiten: moderne Browser probieren IPv6 zuerst. Im Zweifel erst nur den A-Record setzen.
2
Einmalig pro Domain

DNS-Zone beim gewünschten Betreiber anlegen

Zwei Rollen werden ständig verwechselt:

  • Registrar — dort hast du die Domain gekauft (z. B. IONOS, Namecheap, INWX). Er verwaltet die Eigentümerdaten und trägt ein, welche Nameserver zuständig sind.
  • DNS-Betreiber — dort liegen die eigentlichen Records. Das kann der Registrar selbst sein, oder ein anderer Dienst wie die Hetzner DNS Console.

Du kannst also bei jedem Registrar bleiben und die Records trotzdem bei Hetzner pflegen. In der Hetzner DNS Console unter Zonen → Zone hinzufügen die Domain ohne www eintragen (z. B. example.de) und die vorgeschlagene Import-Option überspringen, wenn die Domain neu ist.

Ergebnis
Die Zone existiert und zeigt dir drei Nameserver-Namen an (bei Hetzner hydrogen, oxygen, helium .ns.hetzner.com). Genau die brauchst du im nächsten Schritt.
3
Einmalig pro Domain

Nameserver beim Registrar eintragen

Beim Registrar in der Domain-Verwaltung die eigenen Nameserver-Einträge durch die drei aus Schritt 2 ersetzen. Der Menüpunkt heißt je nach Anbieter Nameserver, DNS-Einstellungen oder Zielserver.

Vorher die alten Records abschreiben
Mit dem Nameserver-Wechsel gilt nur noch die neue Zone. Bestehende MX-Records für E-Mail oder TXT-Records für Dienste musst du in der neuen Zone nachbauen — sonst kommt ab dem Umschalten keine Mail mehr an.

Die Umstellung wirkt nicht sofort: rechne mit ein bis vier Stunden, im ungünstigsten Fall bis zu 48. Prüfen kannst du es so:

Terminal (lokal)
# Welche Nameserver sind für die Domain hinterlegt?
dig NS example.de +short

# Windows ohne dig: nslookup tut es auch
nslookup -type=NS example.de
Ergebnis
Die Ausgabe listet die neuen Nameserver. Ab jetzt zählt allein, was in deiner Zone steht.
4
Pro Domain

Records für Root-Domain und www setzen

Die vier Record-Typen, mit denen du praktisch alles abdeckst:

  • A — Name zeigt auf eine IPv4. Der Standardfall.
  • AAAA — Name zeigt auf eine IPv6. Nur setzen, wenn der Server sie beantwortet.
  • CNAME — Name zeigt auf einen anderen Namen. Praktisch für www, aber nie für die Root-Domain (@).
  • * — Wildcard: fängt jede Subdomain ab, die keinen eigenen Record hat.

Der Name @ steht dabei für die Domain selbst. In der Hetzner DNS Console lässt sich die Zone auch direkt als Textdatei bearbeiten — das geht schneller als die Formularmaske:

Zonendatei (Auszug)
; Name   TTL   Typ     Wert
@        3600  A       203.0.113.10
@        3600  AAAA    2a01:4f8:c17:1234::1
www      3600  CNAME   example.de.
TTL bewusst wählen
Die TTL sagt Resolvern, wie lange sie die Antwort behalten dürfen. Vor einem geplanten Umzug einen Tag vorher auf 300 senken, danach wieder auf 3600 — sonst hängen Besucher stundenlang auf der alten IP fest. Der Punkt am Ende von example.de. ist Absicht: er markiert den vollständigen Namen.
5
Pro Projekt

Subdomain für das Projekt anlegen

Jedes Projekt bekommt seinen eigenen Namen: app.example.de, api.example.de, status.example.de. Alle zeigen auf dieselbe Server-IP — welche Anwendung antwortet, entscheidet später der Reverse-Proxy anhand des angefragten Hostnamens.

Zonendatei (Auszug)
; Eine Subdomain je Projekt — gleiche IP, verschiedene Namen
app      3600  A   203.0.113.10
api      3600  A   203.0.113.10

; Alternative: Wildcard fängt alles ab, was keinen eigenen Record hat
*        3600  A   203.0.113.10
Wildcard, wenn Coolify die Subdomains vergibt
Legst du Apps in Coolify im Minutentakt an, spart ein einzelner *-Record den Gang in die DNS-Konsole bei jedem neuen Projekt. Der Preis: jeder Tippfehler landet ebenfalls auf deinem Server statt auf einer Fehlermeldung.
6
Pro Projekt

Auflösung prüfen, bevor ein Zertifikat angefordert wird

Dieser Schritt sieht nach Kleinkram aus und ist der wichtigste der ganzen Anleitung. Let's Encrypt prüft die Domain über genau diese Auflösung — stimmt sie nicht, scheitert die Ausstellung.

Terminal (lokal)
# Muss exakt die Server-IP zurückgeben
dig app.example.de +short

# Am lokalen Cache vorbei, direkt bei einem öffentlichen Resolver fragen
dig @1.1.1.1 app.example.de +short
Nicht ins Rate-Limit rennen
Let's Encrypt erlaubt pro Domain nur eine begrenzte Zahl gescheiterter Versuche pro Stunde. Wer bei falschem DNS wieder und wieder auf „Deploy" drückt, sperrt sich die Domain für Stunden aus. Erst dig, dann Zertifikat.
Ports müssen offen sein
Für die Zertifikatsprüfung muss der Server über Port 80 erreichbar sein, für den Betrieb über 443. Wie die Firewall dafür eingerichtet wird, steht in Server-Erst-Einrichtung & Absicherung.
7
Pro Projekt

Weg A — HTTPS über Coolify (Standard)

Läuft Coolify auf dem Server, ist das der kürzere Weg: dort ist ein Traefik-Proxy eingebaut, der das Zertifikat selbst besorgt und erneuert. Du trägst nur die Domain ein.

  • In Coolify die Anwendung öffnen → Configuration → General
  • Unter Domains die vollständige URL eintragen: https://app.example.de
  • Save, danach Redeploy — Traefik fordert das Zertifikat beim ersten Aufruf an
Ergebnis
Nach wenigen Sekunden antwortet https://app.example.de mit gültigem Zertifikat. Die Erneuerung alle 90 Tage übernimmt Traefik ohne dein Zutun.
Verwandte Anleitung
Installation, GitHub-Anbindung und das Anlegen der Anwendung stehen in Coolify einrichten & Projekte ausrollen.
8
Pro Projekt

Weg B — HTTPS über Nginx und Certbot

Ohne Coolify — etwa für ein Projekt, das per Docker Compose oder GitHub Action ausgerollt wird — übernimmt Nginx die Rolle des Reverse-Proxys und Certbot die Zertifikate.

Weg A und Weg B nie parallel
Coolifys Traefik und Nginx wollen beide die Ports 80 und 443. Wer zuerst startet, gewinnt; der andere bleibt mit address already in use stehen. Auf einem Server also entweder das eine oder das andere.
Server — Nginx und Certbot installieren
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
/etc/nginx/sites-available/app.example.de
server {
    listen 80;
    server_name app.example.de;

    location / {
        # An die Anwendung, die lokal auf Port 3000 lauscht
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Server — aktivieren und Zertifikat holen
# Site aktivieren und Konfiguration testen
sudo ln -s /etc/nginx/sites-available/app.example.de /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# Zertifikat holen — certbot trägt HTTPS und die Umleitung selbst ein
sudo certbot --nginx -d app.example.de -d www.app.example.de
Server — Erneuerung prüfen
# Der Timer erledigt die Erneuerung zweimal täglich
systemctl status certbot.timer

# Probelauf ohne echte Ausstellung — muss fehlerfrei durchlaufen
sudo certbot renew --dry-run
Ergebnis
Certbot hat die server-Blöcke umgeschrieben: Port 80 leitet auf 443 um, das Zertifikat liegt unter /etc/letsencrypt/live/. Der Probelauf bestätigt, dass die Erneuerung in 90 Tagen funktioniert.
9
Pro Domain

Optional: CAA-Record und saubere Weiterleitungen

Zwei Feinheiten, die die Einrichtung abrunden.

CAA-Record — legt fest, welche Zertifizierungsstelle für deine Domain überhaupt ausstellen darf. Ein Angreifer, der irgendwo anders ein Zertifikat erschleichen will, läuft damit ins Leere.

Zonendatei (Auszug)
; Nur Let's Encrypt darf Zertifikate ausstellen
@   3600  CAA  0 issue "letsencrypt.org"

Weiterleitung www → Root — damit beide Schreibweisen unter derselben Adresse landen. In Coolify genügt es, https://www.example.de als zweite Domain einzutragen; ohne Coolify erledigt das ein kleiner Nginx-Block.

Nginx — www auf die Root-Domain umleiten
server {
    listen 443 ssl;
    server_name www.example.de;
    return 301 https://example.de$request_uri;
}
Auch der www-Name braucht ein Zertifikat
Die Umleitung passiert erst nach dem TLS-Handshake. www.example.de muss also im selben Zertifikat stehen — bei Certbot per zusätzlichem -d, bei Coolify als zweite Domain.
