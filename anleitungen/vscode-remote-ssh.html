VS Code mit dem Hetzner-Server verbinden

⏱ ca. 25 Min Aktualisiert 02.08.2026 Windows · VS Code Remote-SSH → Ubuntu 24.04

Einmal einrichten, danach arbeitest du im gewohnten Editor direkt auf dem Server: Dateien, Terminal, Git und Container laufen dort, die Oberfläche bleibt lokal.

Was vorher stehen muss
Die Server-Erst-Einrichtung ist abgeschlossen: ein eigener Benutzer, Anmeldung nur per Schlüssel, root gesperrt. VS Code meldet sich bewusst als dieser Benutzer an — nicht als root.

Die einmaligen Einrichtungsschritte sind ausgeblendet — sichtbar bleibt der Weg, den du für jedes neue Projekt gehst.

1
Einmalig pro Rechner

Voraussetzungen auf dem Windows-Rechner prüfen

VS Code bringt keinen eigenen SSH-Client mit — es benutzt den von Windows. Beides muss vorhanden und im PATH sein.

PowerShell (lokal)
# Muss eine Version ausgeben, z. B. OpenSSH_for_Windows_9.5
ssh -V

# Muss die VS-Code-Version ausgeben
code -v
PowerShell als Administrator — nur falls ssh fehlt
Add-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0
Kein code-Befehl?
Dann fehlt der Eintrag im PATH. In VS Code F1 drücken und Shell Command: Install 'code' command in PATH ausführen, danach die PowerShell neu öffnen.
2
Einmalig pro Rechner

Extension „Remote - SSH" installieren

Entweder über die Seitenleiste (Strg+Umschalt+X, nach Remote - SSH suchen, Herausgeber Microsoft) oder direkt aus der PowerShell.

PowerShell (lokal)
code --install-extension ms-vscode-remote.remote-ssh
Das grüne Feld unten links
Nach der Installation sitzt in der Statusleiste ganz links ein grünes Feld mit zwei Pfeilen. Es ist ab jetzt dein Ein- und Ausstieg: verbinden, Verbindung wechseln, zurück nach lokal.
3
Einmalig pro Server

Server als Alias in der .ssh\config hinterlegen

VS Code liest diese Datei aus und bietet jeden Host-Eintrag zur Auswahl an. Ein Alias erspart dir außerdem für immer das Tippen von IP, Benutzer und Port.

PowerShell (lokal) — Datei öffnen bzw. anlegen
notepad "$env:USERPROFILE\.ssh\config"
C:\Users\<Name>\.ssh\config
Host web01
    HostName <SERVER-IP>
    User max
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    # Nur diesen einen Schlüssel anbieten — siehe Kasten unten
    IdentitiesOnly yes
    # Hält die Verbindung offen, wenn du länger nichts tippst
    ServerAliveInterval 60
    # Reicht deinen lokalen Schlüssel für Git durch — siehe Schritt 8
    ForwardAgent yes
IdentitiesOnly ist kein Beiwerk
Ohne diese Zeile bietet SSH der Reihe nach alle Schlüssel an, die es findet. Der gehärtete Server erlaubt aber nur MaxAuthTries 3 — bei vier Schlüsseln fliegst du raus, bevor der richtige an der Reihe ist. Die Meldung lautet dann irreführend Too many authentication failures.
Port angepasst?
Wenn du den SSH-Port verlegt hast (letzter Schritt der Server-Erst-Einrichtung), muss er hier stehen. VS Code hat keine andere Quelle dafür.
PowerShell (lokal) — erst hier testen, dann in VS Code
ssh web01
Soll-Ergebnis
Du landest ohne Passwortabfrage auf dem Server. Was in der PowerShell nicht funktioniert, funktioniert auch in VS Code nicht — dort steckt die Fehlermeldung nur tiefer vergraben.
4
Einmalig pro Rechner

Rechte am privaten Schlüssel geraderücken

Der typische Windows-Stolperstein: Dateien im Benutzerordner erben Rechte für Gruppen wie Benutzer oder SYSTEM. OpenSSH verweigert daraufhin die Arbeit mit dem Schlüssel. Wenn Schritt 3 sauber durchlief, überspringst du das hier.

PowerShell (lokal)
# Vererbung kappen — danach hat nur noch, wer explizit eingetragen ist
icacls "$env:USERPROFILE\.ssh\id_ed25519" /inheritance:r

# Dir selbst Lesezugriff geben, sonst niemandem
icacls "$env:USERPROFILE\.ssh\id_ed25519" /grant:r "$($env:USERNAME):(R)"

# Kontrolle: es darf nur dein Benutzername auftauchen
icacls "$env:USERPROFILE\.ssh\id_ed25519"
Das war die Ursache, wenn …
… beim Verbindungsversuch UNPROTECTED PRIVATE KEY FILE oder bad permissions im Log stand. Nur die private Datei ohne Endung ist betroffen, nicht die .pub.
5
Einmalig pro Server

Erste Verbindung aus VS Code herstellen

F1 drücken, Remote-SSH: Connect to Host wählen, in der Liste web01 anklicken. Es öffnet sich ein neues Fenster; die Frage nach der Plattform beantwortest du mit Linux, den Fingerabdruck bestätigst du einmalig.

Beim ersten Mal lädt VS Code seinen eigenen Serverteil auf die Maschine — das dauert ein bis zwei Minuten und passiert genau einmal pro Server.

Server — was dort gelandet ist
ls ~/.vscode-server
du -sh ~/.vscode-server
Die Firewall bleibt zu
Der VS-Code-Server lauscht nicht nach außen — der gesamte Verkehr läuft durch die bestehende SSH-Verbindung. Du musst in der UFW keinen zusätzlichen Port öffnen. Nur root geht nicht: die Extension arbeitet mit deinem normalen Benutzer, so wie der gehärtete Server es vorgibt.
Verbunden
Unten links steht jetzt SSH: web01. Alles, was du in diesem Fenster tust, passiert auf dem Server.
6
Pro Projekt

Projektordner auf dem Server öffnen

Im verbundenen Fenster Datei → Ordner öffnen. Der Dateidialog zeigt jetzt das Server-Dateisystem, nicht deine Festplatte. Danach fragt VS Code einmal, ob du den Autoren des Ordners vertraust.

Integriertes Terminal (Strg+ö) — läuft auf dem Server
# Zur Kontrolle, wo du gelandet bist
whoami
hostname
pwd
Speichern schlägt fehl?
Ordner unter /var/www gehören oft root, dein Benutzer darf dort nur lesen. Entweder den Besitz übertragen oder das Projekt im eigenen Heimatverzeichnis halten.
Server — Besitz übertragen
sudo chown -R max:max /var/www/mein-projekt
7
Pro Projekt

Extensions am richtigen Ort installieren

Die Extension-Seitenleiste teilt sich in der Remote-Sitzung in zwei Blöcke: Lokal — Installiert und SSH: web01 — Installiert. Bei jeder Extension steht dann nicht mehr „Installieren", sondern „In SSH: web01 installieren".

  • Lokal bleiben: Themes, Icon-Sets, Tastaturbelegungen — alles, was nur die Oberfläche betrifft.
  • Auf den Server gehören: Sprachunterstützung, Linter, Formatierer, Debugger, Docker — alles, was Code liest oder ausführt.
Integriertes Terminal — installiert direkt im Remote
code --install-extension ms-python.python

# Was ist auf dem Server aktiv?
code --list-extensions
Warum die Trennung wichtig ist
Eine lokal installierte Sprachunterstützung sieht die Dateien auf dem Server gar nicht — sie meldet dann Fehler an Stellen, an denen keine sind, oder bleibt einfach stumm. Das ist die häufigste Verwirrung nach der ersten Verbindung.
8
Pro Projekt

Git und GitHub aus der Remote-Sitzung nutzen

Die Quellcodeverwaltung in VS Code bedient das Git auf dem Server. Zum Pushen braucht der Server also einen Schlüssel, den GitHub kennt — den musst du aber nicht dorthin kopieren. Das ForwardAgent yes aus Schritt 3 reicht deinen lokalen Schlüssel für die Dauer der Sitzung durch.

PowerShell als Administrator — Agent dauerhaft aktivieren
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
PowerShell (lokal) — Schlüssel in den Agenten legen
ssh-add "$env:USERPROFILE\.ssh\id_ed25519"

# Muss den Schlüssel auflisten
ssh-add -l
Integriertes Terminal (Server) — Absender setzen und testen
git config --global user.name "Max Mustermann"
git config --global user.email "max@example.com"

# Nutzt den durchgereichten Schlüssel — GitHub grüßt mit deinem Namen
ssh -T git@github.com
Der Schlüssel bleibt zu Hause
Weitergereicht wird nur die Signieranfrage, nie die Schlüsseldatei. Auf dem Server liegt dadurch nichts, was jemand stehlen könnte.
Nur auf eigenen Servern
Solange die Sitzung offen ist, kann jeder mit root-Rechten auf dieser Maschine den Agenten mitbenutzen. Auf deinem eigenen Hetzner-Server ist das in Ordnung — auf einem fremden gehört ForwardAgent yes nicht in die Konfiguration. Die Alternative dort ist ein eigener Deploy-Key, wie in der Deploy-Anleitung beschrieben.
9
Pro Projekt

Ports weiterleiten und im lokalen Browser öffnen

Neben dem Terminal liegt der Reiter Ports. Mit Port weiterleiten trägst du dort die Portnummer ein, die auf dem Server lauscht — VS Code öffnet dann denselben Port auf deinem Rechner und leitet ihn durch den SSH-Tunnel.

Integriertes Terminal (Server) — was lauscht überhaupt?
ss -tlnp
Genau dafür ist die 127.0.0.1-Bindung da
Dienste, die laut Docker-Anleitung nur an 127.0.0.1 gebunden sind, erreichst du so im lokalen Browser unter http://localhost:8000 — ohne die UFW zu öffnen und ohne den Dienst ins Internet zu stellen.
Meistens automatisch
Startest du eine Anwendung im integrierten Terminal und sie gibt eine localhost-Adresse aus, richtet VS Code die Weiterleitung von selbst ein und blendet eine Benachrichtigung mit Link ein. Der Ports-Reiter ist der Handgriff für alles, was schon vorher lief.
10
Pro Projekt

In Containern arbeiten: andocken oder darin entwickeln

Läuft das Projekt nach der Docker-Anleitung in Containern, kommst du auch dort hinein — VS Code hängt sich dann in den Container, der auf dem Server läuft. Dafür brauchst du die Extension Dev Containers, installiert im Remote.

Integriertes Terminal (Server)
code --install-extension ms-vscode-remote.remote-containers

# Muss ohne sudo laufen, sonst findet die Extension keine Container
docker ps

Weg A — an einen laufenden Container andocken. F1 → Dev Containers: Attach to Running Container… → Container auswählen. Gut zum Nachsehen und für schnelle Eingriffe.

Weg B — im Container entwickeln. Eine devcontainer.json ins Repo legen, dann F1 → Dev Containers: Reopen in Container. Der Editor benutzt danach die Werkzeuge und Bibliotheken aus dem Container statt die des Servers.

.devcontainer/devcontainer.json
{
  "name": "mein-projekt",
  "dockerComposeFile": "../compose.yaml",
  "service": "api",
  "workspaceFolder": "/app",
  "customizations": {
    "vscode": {
      "extensions": ["ms-python.python"]
    }
  },
  // Container nach dem Schließen weiterlaufen lassen
  "shutdownAction": "none"
}
permission denied beim Docker-Socket
Dann fehlt deinem Benutzer die Gruppe docker (Docker-Anleitung, Schritt 3). Nach dem Nachtragen greift die neue Gruppe erst in einer neuen Anmeldung: in VS Code das Remote-Fenster schließen und frisch verbinden — ein Neuladen des Fensters genügt nicht.
Was shutdownAction verhindert
Ohne diese Zeile stoppt VS Code den Container beim Schließen des Fensters. Bei einem produktiv laufenden Dienst ist das selten gewollt.
11
Bei Bedarf

Fehlersuche: die fünf üblichen Verdächtigen

Erste Regel: nicht in VS Code raten, sondern in der PowerShell nachsehen. ssh -v web01 zeigt in Klartext, woran es scheitert.

PowerShell (lokal) — ausführliche Ausgabe
ssh -v web01
  • Permission denied (publickey) — falscher Benutzer, falscher Schlüssel in IdentityFile oder der öffentliche Schlüssel fehlt auf dem Server in ~/.ssh/authorized_keys.
  • Too many authentication failures — IdentitiesOnly yes fehlt in der Konfiguration, siehe Schritt 3.
  • UNPROTECTED PRIVATE KEY FILE — die Dateirechte unter Windows, siehe Schritt 4.
  • Connection refused oder Zeitüberschreitung — falscher Port in der Konfiguration, oder fail2ban hat dich nach drei Fehlversuchen für eine Stunde ausgesperrt.
  • Could not establish connection … server install failed — auf dem Server ist die Platte voll oder der Serverteil ist beschädigt.
Server (über die Hetzner-Konsole, falls SSH nicht mehr geht)
# Bin ich selbst gesperrt?
sudo fail2ban-client status sshd

# Sperre wieder aufheben
sudo fail2ban-client set sshd unbanip <DEINE-IP>
Server — Serverteil neu aufsetzen
# Platz auf der Platte prüfen
df -h

# Serverteil verwerfen — beim nächsten Verbinden lädt VS Code ihn neu
rm -rf ~/.vscode-server
Das Log in VS Code
F1 → Remote-SSH: Show Log öffnet das Ausgabefenster mit dem vollständigen Verbindungsprotokoll. Dort steht dieselbe Meldung wie im Terminal — nur muss man wissen, wo man sucht.
