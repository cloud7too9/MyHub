Docker einrichten & pro Repository integrieren

⏱ ca. 40 Min Aktualisiert 02.08.2026 Ubuntu 24.04 LTS · Docker Engine

Einmalig Docker auf dem Server aufsetzen — danach jedes Projekt nach demselben Muster containerisieren und über die bestehende GitHub-Action ausrollen.

Die einmaligen Server-Schritte sind ausgeblendet — sichtbar bleibt der Weg, den du für jedes neue Projekt gehst.

1
Einmalig pro Server

Alte Pakete entfernen und Docker-Repository einrichten

Das docker.io-Paket aus den Ubuntu-Quellen ist meist veraltet und bringt kein Compose-Plugin mit. Deshalb direkt von Docker.

Server — Altlasten entfernen
for pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do
  sudo apt remove -y $pkg 2>/dev/null
done
Server — Schlüssel und Quelle eintragen
sudo apt update
sudo apt install -y ca-certificates curl

# GPG-Schlüssel ablegen
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Paketquelle im aktuellen .sources-Format
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update

Einmalig pro Server

Benutzer in die docker-Gruppe aufnehmen

Damit du Docker ohne sudo bedienen kannst — und damit die GitHub-Action als dein Deploy-Benutzer arbeiten kann.

Server
sudo usermod -aG docker $USER

# Neu anmelden, damit die Gruppe greift — dann testen
docker ps
Das ist faktisch root
Wer in der Gruppe docker ist, kann das Dateisystem des Hosts in einen Container einhängen und damit alles tun. Nimm dort nur Benutzer auf, denen du volle Rechte geben würdest.
4
Einmalig pro Server

Die UFW-Falle verstehen

Wichtigster Punkt dieser Anleitung: Docker schreibt eigene iptables-Regeln und hängt sich vor UFW. Ein veröffentlichter Port ist damit offen im Internet — auch wenn ufw status das Gegenteil suggeriert.

Regel für alle Projekte
# Offen im Netz, UFW greift NICHT:
#   ports: - "8000:8000"

# Nur lokal erreichbar, davor ein Reverse-Proxy:
#   ports: - "127.0.0.1:8000:8000"
Muster
Container binden immer an 127.0.0.1. Nach außen zeigt nur ein Reverse-Proxy (Caddy, nginx, Traefik) auf 80/443 — und genau die beiden Ports gibst du in UFW frei.
Server — prüfen, was wirklich lauscht
# Alles mit 0.0.0.0 ist von außen erreichbar
sudo ss -tulnp | grep docker

Pro Projekt

Dateien im Repository anlegen

Vier Dateien reichen. Sie liegen im Wurzelverzeichnis des Repos und kommen mit ins Git — bis auf die .env.

Aufbau
mein-projekt/
├── Dockerfile          # wie das Abbild gebaut wird
├── .dockerignore       # was NICHT ins Abbild darf
├── compose.yaml        # wie der Container läuft
├── .env                # Geheimnisse — NICHT committen
└── .env.beispiel       # Vorlage — kommt ins Git
Zuerst absichern
.env sofort in die .gitignore eintragen — bevor der erste Commit läuft. Einmal gepusht, bleibt ein Geheimnis für immer in der Git-Historie.
6
Pro Projekt

Dockerfile schreiben

Beispiel für eine Python-/FastAPI-Anwendung. Die Reihenfolge der Zeilen ist kein Zufall — sie entscheidet über die Bauzeit.

Dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Erst die Abhängigkeiten — diese Schicht bleibt im Cache,
# solange requirements.txt sich nicht ändert
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Dann erst der Code — ändert sich bei jedem Commit
COPY . .

# Nicht als root laufen lassen
RUN adduser --system --group --no-create-home app \
 && chown -R app:app /app
USER app

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
Warum die Reihenfolge
Docker baut in Schichten und verwirft ab der ersten Änderung alles Folgende. Kämen COPY . . zuerst, würde jeder Commit die Installation aller Pakete neu auslösen.
Innen 0.0.0.0, außen 127.0.0.1
Im Container muss die Anwendung auf 0.0.0.0 lauschen, sonst erreicht Docker sie nicht. Die Begrenzung passiert erst beim Veröffentlichen des Ports in Schritt 8.

Pro Projekt

compose.yaml schreiben

Hier steht, wie der Container betrieben wird: Neustartverhalten, Port-Bindung, Umgebungsvariablen, dauerhafte Daten.

compose.yaml
services:
  api:
    build: .
    image: mein-projekt:latest
    container_name: mein-projekt-api
    # Startet nach Reboot und nach Absturz wieder
    restart: unless-stopped
    env_file: .env
    ports:
      # Nur lokal — siehe Schritt 4
      - "127.0.0.1:8000:8000"
    volumes:
      - daten:/app/daten
    healthcheck:
      test: ["CMD-SHELL", "python -c 'import urllib.request; urllib.request.urlopen(\"http://localhost:8000/health\")'"]
      interval: 30s
      timeout: 5s
      retries: 3
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

volumes:
  daten:
Zwei Details
Die Zeile version: ganz oben ist überholt und wird nur noch ignoriert. Und ohne logging-Begrenzung wachsen Logdateien unbemerkt, bis die Platte voll ist.
Dauerhafte Daten
Alles, was nicht in einem volume liegt, ist beim nächsten Neubau weg. Datenbanken, Uploads und erzeugte Dateien gehören dort hinein.

Pro Projekt

Lokal bauen und testen

Erst lokal grün, dann auf den Server. Spart viel Fehlersuche über SSH.

Terminal (lokal)
# Bauen und im Vordergrund starten — Logs direkt sichtbar
docker compose up --build

# In einem zweiten Fenster: Zustand und Zugriff
docker compose ps
curl http://localhost:8000/health

# In den Container hineinschauen
docker compose exec api sh

# Beenden
docker compose down

Pro Projekt

Erstmalig auf dem Server ausrollen

Einmal von Hand — danach übernimmt die Action. Das ist derselbe Vorab-Klon, den auch die Deploy-Anleitung verlangt.

Server
cd /var/www
git clone git@github.com:benutzer/mein-projekt.git
cd mein-projekt

# .env aus der Vorlage anlegen und ausfüllen
cp .env.beispiel .env
nano .env

# Bauen und im Hintergrund starten
docker compose up -d --build
docker compose ps

Pro Projekt

GitHub-Action auf Docker umstellen

In der bestehenden deploy.yml wird nur der script-Block erweitert — der Rest bleibt, wie er ist.

.github/workflows/deploy.yml (Ausschnitt)
          script: |
            cd /var/www/mein-projekt
            git pull origin main
            docker compose up -d --build
            # Alte, unbenutzte Abbilder aufräumen
            docker image prune -f
Ergebnis
Push auf main → Action baut das Abbild auf dem Server neu und tauscht den Container. --build ist entscheidend, sonst läuft der alte Stand weiter.
Verwandte Anleitung
Deploy-Key, Secrets und Grundgerüst der Action stehen in Automatisches Deploy auf Hetzner per GitHub Actions.

Pro Projekt

Betrieb und Wartung

Die Handvoll Befehle, die du danach wirklich brauchst.

Server — Alltag
docker compose ps                      # Zustand
docker compose logs -f --tail 100 api  # Logs mitlesen
docker compose restart api             # Neustart
docker compose down                    # Stoppen (Volumes bleiben)
docker system df                       # Platzverbrauch
Beim Aufräumen aufpassen
Zum Platzschaffen docker image prune -af nutzen. Der oft empfohlene Zusatz --volumes löscht auch deine Daten-Volumes — also Datenbank und Uploads.
