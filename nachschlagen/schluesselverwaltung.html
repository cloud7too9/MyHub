Privater und öffentlicher Schlüssel

Ein Schlüsselpaar sind zwei Dateien, die zusammengehören. Der private Teil bleibt auf dem Gerät, auf dem er entstanden ist. Der öffentliche Teil darf überall hin — er ist nicht geheim, aus ihm lässt sich der private nicht zurückrechnen.

Beim Login stellt der Server eine Aufgabe, die sich nur mit dem privaten Schlüssel lösen lässt. Der Schlüssel selbst geht dabei nie über die Leitung. Genau das ist der Unterschied zum Passwort: Ein Passwort schickst du der Gegenstelle — und damit auch einer falschen.

Welche Datei ist was

  • ~/.ssh/id_ed25519 — privat, Rechte 600, verlässt das Gerät nie
  • ~/.ssh/id_ed25519.pub — öffentlich, eine einzige Textzeile, darf verschickt werden
  • ~/.ssh/known_hosts — Gegenstellen, die du schon gesehen hast; warnt, wenn sich der Server ändert
  • ~/.ssh/config — Kurznamen und Optionen je Server
  • ~/.ssh/authorized_keys — nur auf dem Server: wer bei diesem Konto herein darf

Verfahren

ed25519 ist die Vorgabe: kurz, schnell, sicher. rsa nur, wenn eine alte Gegenstelle nichts anderes kann — dann mit -b 4096. dsa ist abgeschafft, ecdsa gibt es ohne Not keinen Grund zu nehmen.

Passphrase und Agent

Der private Schlüssel ist eine Datei. Ohne Passphrase reicht ein kopierter Ordner, um dein Konto zu übernehmen — mit Passphrase ist die Datei allein wertlos. Damit du sie nicht bei jedem Login tippst, hält der ssh-agent den entsperrten Schlüssel für die Sitzung.

Terminal (lokal)
# Schlüssel in den Agent legen (einmal je Sitzung)
ssh-add ~/.ssh/id_ed25519

# Was liegt gerade im Agent?
ssh-add -l

# Passphrase nachträglich setzen oder ändern
ssh-keygen -p -f ~/.ssh/id_ed25519

# Fingerabdruck — die Kurzform, an der du einen Schlüssel wiedererkennst
ssh-keygen -lf ~/.ssh/id_ed25519.pub

Der Fingerabdruck ist für privaten und öffentlichen Teil derselbe. Damit lässt sich prüfen, ob eine Zeile auf dem Server zu dem Schlüssel gehört, den du gerade in der Hand hast.

Ablage pro Nutzer statt global

Es gibt keine zentrale Liste erlaubter Schlüssel, die für den ganzen Server gilt. Jedes Konto hat seine eigene: /home/<nutzer>/.ssh/authorized_keys. Das ist keine Umständlichkeit, sondern der Sinn der Sache — jede Tür hat ihr eigenes Schloss, und wer bei einem Konto eingetragen ist, kommt deshalb noch lange nicht in ein anderes.

Eine Folge davon: Wer einen zweiten Nutzer anlegt, muss dessen Schlüssel getrennt hinterlegen. Der Schlüssel im root-Konto gilt für root, sonst für niemanden.

Rechte — der häufigste stille Fehler

sshd prüft mit StrictModes yes (Standard), ob die Dateien niemand anderem offenstehen. Passt etwas nicht, wird die authorized_keys kommentarlos übergangen: Der Login endet mit Permission denied (publickey), obwohl der Schlüssel richtig dort steht.

Server — Soll-Zustand herstellen
# Home darf nicht für die Gruppe schreibbar sein
chmod 750 /home/max

install -d -m 700 -o max -g max /home/max/.ssh
chown max:max /home/max/.ssh/authorized_keys
chmod 600 /home/max/.ssh/authorized_keys

# Kontrolle: drwx------ und -rw-------, Besitzer beide Male max
ls -ld /home/max/.ssh
ls -l /home/max/.ssh/authorized_keys

Doch zentral?

Über AuthorizedKeysFile /etc/ssh/authorized_keys.d/%u lässt sich die Ablage aus den Home-Verzeichnissen herausziehen — dann verwaltet nur noch root, wer herein darf. Für eine Handvoll Konten ist das mehr Verwaltung als Nutzen; ab vielen Servern nimmt man ohnehin ein Werkzeug dafür oder steigt auf SSH-Zertifikate um.

Rollen und Rechte

Wer hereinkommt, soll genau das können, wofür er da ist. Drei Rollen decken den Normalfall ab:

RollesudoPasswortwofür
AdminGruppe sudoja — als BremseSystemänderungen
Eingeschränktnein oder gezieltjaAlltag, eigene Dateien
DienstneinkeinsDeploys, ohne Mensch davor

Die Gruppe sudo ist der Alles-Schalter: erlaubt jeden Befehl, fragt einmal nach dem eigenen Passwort. Dazwischen liegt die nützlichste Stufe — einzelne Befehle, festgeschrieben in einer Datei unter /etc/sudoers.d/.

Server — was darf wer?
# Gruppen eines Kontos
id lena

# Die einzige verlässliche Auskunft über sudo-Rechte
sudo -l -U lena

# Alle Regeln gegenlesen — muss "parsed OK" melden
sudo visudo -c

Vier Regeln für sudoers.d

  • Immer visudo -f statt eines Editors: prüft beim Speichern und legt 0440 an. Ein Syntaxfehler sperrt sonst jedes sudo im System aus.
  • Kein Punkt im Dateinamen. sudoers.d überliest jede Datei mit . oder ~ im Namen — 50-lena.conf wirkt nie, ohne Fehlermeldung.
  • Volle Pfade zu den erlaubten Befehlen. Ohne Pfad ließe sich ein gleichnamiges Programm im eigenen Verzeichnis unterschieben.
  • Keine Editoren, Shells oder offenen Werkzeuge. Aus vi, less, find oder einem uneingeschränkten systemctl heraus lässt sich alles Weitere starten — die Beschränkung ist dann nur noch Zierde.
Die Gruppe docker ist root
Wer Container starten darf, kann sich einen mit dem Wurzelverzeichnis des Servers geben — ohne Passwortabfrage und ohne Spur in den sudo-Logs. Dasselbe gilt für Schreibrechte an Skripten, die per sudo laufen. Jede Abstufung darüber ist wirkungslos.

Gruppenwechsel greifen erst bei der nächsten Anmeldung. Wer gerade eingeloggt ist, behält seine alten Rechte bis zum Neuanmelden.

Ein Nutzer, mehrere Geräte

Das Konto steht für die Person, nicht für den Laptop. Kommt ein zweites Gerät dazu, entsteht kein zweites Konto — es kommt eine weitere Zeile in dieselbe authorized_keys.

Jedes Gerät bekommt sein eigenes Paar. Der private Schlüssel wird nie von einem Gerät auf ein anderes kopiert. Drei Gründe:

  • Ein verlorenes Gerät lässt sich einzeln aussperren, ohne allen anderen den Zugang zu nehmen.
  • Der private Schlüssel muss nie über eine Leitung, einen Chat oder einen USB-Stick — er kann unterwegs also auch nicht abhandenkommen.
  • In den Logs steht, welches Gerät sich angemeldet hat, nicht nur welche Person.

Umgekehrt gilt: Ein Gerät braucht nicht je Server ein eigenes Paar. Derselbe öffentliche Schlüssel darf auf beliebig vielen Servern liegen.

/home/max/.ssh/authorized_keys
# Eine Zeile je Gerät. Der Kommentar am Ende ist die Gerätezuordnung —
# ohne ihn stehen hier mehrere nicht unterscheidbare Zeilen.
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… max@laptop
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… max@tablet

Der Kommentar ist reiner Text und lässt sich jederzeit nachträglich ändern — er wandert nur beim Anlegen automatisch mit (ssh-keygen -C "max@tablet").

Am fremden Rechner

Dort keinen Schlüssel anlegen und schon gar keinen hinkopieren. Zwei Wege ohne bleibende Spuren: ssh -A reicht den Agent des eigenen Geräts durch (nur zu Servern, denen du traust — wer dort root ist, kann ihn mitbenutzen), oder der Schlüssel liegt auf einem mitgeführten Datenträger. Der Weg dahin steht in Git von der portablen SSD nutzen.

Ein Gerät wieder aussperren

Gerät verloren, Laptop weitergegeben, Kollege ausgeschieden — hier zahlt sich aus, dass jede Zeile für genau ein Gerät steht.

Server
# Welche Zeile ist welche? Zeigt Fingerabdruck und Kommentar
ssh-keygen -lf ~/.ssh/authorized_keys

# Die betroffene Zeile löschen
nano ~/.ssh/authorized_keys

# Läuft noch eine Sitzung von diesem Gerät?
who
sudo pkill -KILL -u lena

Das Löschen wirkt sofort für neue Verbindungen — eine bereits offene Sitzung läuft weiter, bis sie beendet wird. Bei einem verlorenen Gerät gehört das Beenden dazu.

Ein ganzes Konto stilllegen

usermod -L allein genügt nicht
Es sperrt nur das Passwort. Der Schlüssel-Login funktioniert weiter — und der ist auf einem gehärteten Server ohnehin der einzige Weg herein. Das Konto muss ablaufen oder die Schlüsselliste leer sein.
Server (als root)
# Konto auf abgelaufen setzen — sperrt auch den Schlüssel-Login
usermod --expiredate 1 lena

# Kontrolle
chage -l lena

# Wieder öffnen
usermod --expiredate "" lena

Und noch ein Punkt, den man leicht übersieht: Derselbe öffentliche Schlüssel liegt womöglich auf weiteren Servern und bei GitHub. Ein verlorenes Gerät ist erst dann erledigt, wenn seine Zeile überall verschwunden ist — der Kommentar hilft beim Suchen.

Was ein Schlüssel dürfen darf

Vor dem Schlüssel können in derselben Zeile Optionen stehen, durch Komma getrennt. Sie gelten nur für diese eine Zeile — derselbe Nutzer kann also einen vollen und einen eingeschränkten Zugang haben.

  • restrict — schaltet alles ab (Terminal, Tunnel, Weiterleitungen). Der beste Anfang; einzelne Fähigkeiten lassen sich danach wieder zulassen (restrict,pty).
  • command="…" — erzwingt genau diesen Befehl, egal was der Aufrufer schickt. Dessen ursprünglicher Wunsch steht in $SSH_ORIGINAL_COMMAND, falls ein Skript ihn auswerten will.
  • from="203.0.113.5" — nur von dieser Adresse. Nützlich bei fester IP, unbrauchbar bei wechselnder.
  • no-pty, no-port-forwarding, no-agent-forwarding — einzeln, wenn restrict zu viel wäre.
  • expiry-time="20271231" — läuft von selbst ab. Für Zugänge auf Zeit besser als ein Kalendereintrag.
/home/deploy/.ssh/authorized_keys
# Ein Deploy-Zugang: genau ein Skript, keine Shell, keine Tunnel.
# Optionen und Schlüssel stehen in EINER Zeile.
restrict,command="/usr/local/bin/deploy.sh" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… deploy@ci

Ein so eingeschränkter Zugang ist der Grund, warum ein Dienst-Nutzer kein Sicherheitsrisiko sein muss: Selbst wer den privaten Schlüssel erbeutet, bekommt keine Shell — nur das eine Skript.

Wenn der Login nicht geht

Permission denied (publickey) ist die eine Meldung für ein Dutzend Ursachen. Der Reihe nach:

  • Richtiges Konto? ssh max@… statt ssh root@… — auf einem gehärteten Server ist root gesperrt.
  • Wird der richtige Schlüssel angeboten? ssh -v zeigt jede Offering public key-Zeile; mit -i lässt sich gezielt einer wählen.
  • Rechte auf dem Server — siehe Ablage pro Nutzer. Der häufigste Fall, und der leiseste.
  • Zeile umgebrochen? Beim Kopieren über Chat oder Mail bricht die Schlüsselzeile gern um. ssh-keygen -lf ~/.ssh/authorized_keys zählt dann weniger Schlüssel als erwartet.
  • AllowUsers oder AllowGroups gesetzt? Wer nicht in der Liste steht, kommt gar nicht erst zur Schlüsselprüfung.
  • Konto abgelaufen oder gesperrt? chage -l max und passwd -S max.
  • fail2ban? Typisches Zeichen: Die Verbindung läuft in einen Timeout, statt abgewiesen zu werden. sudo fail2ban-client status sshd.
Beide Seiten mitlesen
# Lokal: was wird angeboten, was sagt die Gegenstelle?
ssh -v max@<SERVER-IP>

# Auf dem Server, aus einer noch offenen Sitzung heraus
sudo journalctl -u ssh -f

Sperrst du dich komplett aus, bleibt die Konsole im Cloud-Panel des Anbieters. Sie hängt nicht an SSH, verlangt aber ein Konto mit Passwort — ein Grund, das root-Passwort aufzuheben, auch wenn der root-Login über SSH gesperrt ist.

Design und Fortschritt werden lokal auf diesem Gerät gespeichert.
